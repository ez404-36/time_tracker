# План: полное переписывание TimeTracker с Python на Rust

Консолидированный план переноса десктопного приложения TimeTracker (трекинг активности,
TODO-задач с дедлайнами, статистика, звуковые уведомления) со стека Python
(Flet 0.82 + peewee + dependency-injector, ~4500 строк) на Rust.

Документ описывает единый цельный проект переписывания, а не инкрементальную миграцию:
все архитектурные решения зафиксированы заранее, известные дефекты Python-версии
помечены к исправлению, а риски — к проверке на ранних этапах.

---

## 1. Принятые решения

| Аспект | Решение |
|---|---|
| GUI | **Dioxus** (desktop-рендерер на системном webview) |
| База данных | **Чистый старт**: новая SQLite БД, данные не переносятся |
| Схема | **5 таблиц**: `task`, `window_session`, `idle_session`, `settings`, `settings_audio_param`. Таблица `event` из Python-версии **удаляется** — её никто не читал, только писали |
| Платформы | **Linux (X11 + Wayland) + Windows**; macOS — заглушка |
| Процесс | **Big bang** в новой ветке `rust-rewrite`; Python-версия замораживается |
| Системный трей | Да: меню, статусные иконки, close-to-tray |
| Автозапуск | Да: свёрнутый старт, автостарт трекинга |
| Аудит | Файловые логи `tracing` вместо таблицы `event` |

Чистый старт выбран осознанно: таблица `event` служила только «чёрным ящиком» для отладки
и дублировала файловые логи, а перенос ~4500 строк активных записей peewee в
репозитории не принёс бы архитектурной ценности. Аудит переносится в `tracing-appender`.

## 2. Структура cargo workspace

Восемь крейтов, разделённых по слоям ответственности:

```
crates/
  tt-core/       домен: типы, события, ошибки, шина
  tt-db/         схема, миграции, репозитории
  tt-platform/   окна + бездействие (trait + cfg-реализации)
  tt-audio/      воспроизведение звука
  tt-tracker/    сервисы: main/window/idle/pomodoro/deadline
  tt-updater/    проверка релизов GitHub
  tt-system/     системный трей, автозапуск, single-instance
  tt-app/        Dioxus UI + бинарник
assets/          иконки, звуки, CSS
```

Разделение повторяет слои Python-версии (`apps/`, `core/`, `ui/`), но без глобального
`SessionStore` и активных записей: каждый крейт экспортирует типы и трейты, а
побочные эффекты (БД, окна, звук) изолированы за интерфейсами.

**tt-core** — ядро домена. Содержит типы событий, модель состояний, определения ошибок
и шину событий на основе `tokio::sync::broadcast`. Все бизнес-типы (статусы Pomodoro,
данные о окнах, настройки) живут здесь.

**tt-db** — слой доступа к данным. Определяет схему БД (5 таблиц), миграции через
`sqlx::migrate!`, и репозитории с CRUD-операциями. Репозитории возвращают `Result`,
ошибки типизированы.

**tt-platform** — абстракция платформенных API. Трейт `WindowControl` скрывает различия
между X11, Wayland и Windows. Реализации используют `x11rb` (с MIT-SCREEN-SAVER),
`zbus` для Wayland, и `windows` крейт для Windows API.

**tt-audio** — воспроизведение звука. Обёртка над `rodio`, поддерживает mp3/wav/ogg.
Управляет громкостью через `volume_offset` (децибелы → линейная шкала).

**tt-tracker** — бизнес-логика трекинга. Содержит сервисы: `WindowTracker`
(отслеживание активного окна), `IdleTracker` (бездействие), `PomodoroTracker`
(с собственной машиной состояний и таймером), `MainTracker` (координация),
`DeadlineChecker` (проверка дедлайнов).

**tt-updater** — проверка обновлений. Запрашивает releases с GitHub API через `reqwest`,
сравнивает версии с помощью `semver`.

**tt-system** — системная интеграция. Трей, автозапуск, защита от второго экземпляра.
Linux: `~/.config/autostart/*.desktop` и StatusNotifierItem. Windows: реестр `Run`
и именованный мьютекс.

**tt-app** — пользовательский интерфейс. Dioxus-приложение с навигацией, темой,
диалогами. Включает все экраны: задачи, настройки, трекер, статистика.

## 4. Ключевые архитектурные изменения

### 4.1. Шина событий: EventBus → tokio::sync::broadcast

В Python шина (`dict[тип, list[callback]]`) ловит исключения в подписчиках и
переопубликует их как `error.system`. Тип события и payload разделены и рассинхрон
выявляется только в рантайме: подписчик может быть зарегистрирован с неверным числом
аргументов, а проверка делается через `inspect.signature`.

В Rust тип события и payload сливаются в одно перечисление:

```rust
pub enum SystemEvent {           // тип и payload слиты
    AppOpen { ts: DateTime<Utc> },
    WindowSwitch { window: WindowData, ts: DateTime<Utc> },
    PomodoroChangeStatus { prev: PomodoroStatus, new: PomodoroStatus },
    ...
}
```

Компилятор гарантирует, что подписчик `WindowSwitch` не получит payload от `AppOpen`.
Магия с `inspect.signature` (проверка числа аргументов callback) исчезает полностью.

### 4.2. Pomodoro: логика из UI — в сервис

Сейчас логика Pomodoro разорвана: `PomodoroTracker` хранит статус, но отсчёт времени
владеет UI-компонент (`ui/components/timer.py` —
`CountdownComponent(on_end=self._main_tracker.hold)`). Таймер живёт в дереве Flet-контролов,
а состояние — в сервисе. Последствия: закрытие вкладки убивает таймер, а таймер нельзя
протестировать без GUI.

В Rust `PomodoroTracker` владеет собственным `tokio::time::interval` и публикует
`PomodoroTick { remaining }`. UI только отображает значение сигнала. Это разблокирует
юнит-тесты машины состояний Pomodoro.

### 4.3. SessionStore удаляется полностью

`core/store.py` — это `dict[str, Any]`, куда `SessionStoredComponent` складывает сами
Flet-контролы, чтобы дотянуться до них из других модулей. Это глобальное изменяемое
состояние по строковому ключу без типов.

Замена:

- состояние UI → сигналы Dioxus (`Signal<Vec<Task>>`);
- состояние сервисов → поля сервисов;
- связь сервис → UI → подписка на broadcast.

Побочный эффект: паразитная запись в БД (каждое `SessionStore.set()` порождало
`INSERT` в `event`) исчезает вместе с таблицей `event`.

### 4.4. Слой доступа к данным: репозитории

Модели peewee — активные записи: БД дёргается прямо из UI-колбэков. В Rust используются
чистые структуры плюс `TaskRepository` / `SessionRepository` с методами, возвращающими
`Result<_, DbError>`. UI получает данные через `use_resource`, а не через прямые запросы.

### 4.5. Статистика: агрегация в SQL

Сейчас статистика выгружает все сессии за день в память и группирует через `Counter`,
причём делает это каждую секунду (в коде есть TODO про «большую нагрузку»).

В Rust агрегация переносится в `GROUP BY` на уровне SQL, а обновление происходит по
событию `WindowSwitch`, а не по таймеру.

## 5. Баги Python-версии, исправляемые в Rust

Эти дефекты **не переносятся** — каждое поведение покрывается тестом в Rust.

| # | Место | Проблема |
|---|---|---|
| B1 | `apps/time_tracker/services/window_tracker.py:90` | `if len(new_active_windows) != self.active_windows:` — сравнение `int` со `list`, всегда истинно → событие `change_opened_windows` шлётся каждую секунду безусловно |
| B2 | `core/tasks.py:40` | `Task.update(...).where(Task.id in [...])` — Python-оператор `in` над полем peewee даёт `bool`, а не SQL `IN`. WHERE вырождается → обновляются не те строки |
| B3 | `apps/time_tracker/models.py:24` (`SessionAbstract.stop`) | `duration = (ts - self.start_ts).seconds` — `.seconds` отбрасывает дни. Сессия >24 ч считается неверно; отрицательная дельта даёт огромное число. Нужно `total_seconds()` |
| B4 | `apps/events/subscribers.py:63` | `on_app_change_settings` пишет `EventType.CLOSE_APP` вместо `CHANGE_SETTINGS` — copy-paste. **АННУЛИРОВАН**: домен `events` целиком удаляется |
| B5 | `apps/time_tracker/controls/statistics/index.py:132` | `fn.date(start_ts) == filter_date_value` — `start_ts` в UTC, фильтр в локальной дате. Сдвиг суток для не-UTC поясов |
| B6 | `apps/app_settings/models.py:67` | `@lru_cache` на `classmethod` кэширует инстанс на весь процесс; после `save()` в другом месте — устаревший объект |
| B7 | `apps/tasks/services/deadline_checker.py:26` | `Value(Task.deadline_time == _time).alias(...)` — `Value()` оборачивает выражение как литерал; `is_expired_at_now` считается не так |
| B8 | `apps/time_tracker/services/window_control/linux.py` | `except Exception: print(e)` в 3 местах + пустой `try` вокруг `if window:`. Ошибки уходят в stdout, который подавлен в GUI-сборке |

B1–B3 функциональные и ломают данные — покрыть тестами в Rust в первую очередь.

## 6. Этапы (с явными зависимостями)

### Этап 0. Фундамент

Workspace, `rust-toolchain`, `rustfmt`, `clippy -D warnings`, CI (fmt + clippy + test +
сборка Linux + Windows). **Пробный бинарник**: окно Dioxus + `tray-icon` +
`single-instance`. Цель — проверить риски R1 / R8 / R10 **до** написания приложения.
**ОБЯЗАТЕЛЬНО остановиться и доложить пользователю.**

**Критерий готовности**: бинарник запускается на Ubuntu 22.04/24.04 и Windows 10/11,
трей иконка видна, вторая копия не запускается, webview загружается.

### Этап 1. Домен и шина (tt-core)

Перечисление `SystemEvent` (~25 вариантов), `PomodoroStatus` + таблица переходов,
шина на `broadcast` (обработка `RecvError::Lagged`), `thiserror`. Тесты машины состояний
Pomodoro.

**Критерий готовности**: все события типизированы, тесты покрывают все переходы Pomodoro,
шина пересылает события между несколькими подписчиками без ошибок.

### Этап 2. База данных (tt-db)

Миграции `sqlx`: 5 таблиц + 4 новых поля в `settings` (`autostart_enabled`,
`start_minimized`, `close_to_tray`, `autostart_tracking`). Значения `event.type` / `actor`
→ Rust-enum с `TryFrom`; `event.data` → типизированный JSON через `serde`. Репозитории,
WAL, пул. CRUD-тесты; `TaskRepository::mark_expired` покрывает B2. **Таблицы `event`
нет.**

**Критерий готовности**: миграции проходят вперёд и назад, репозитории возвращают
`Result`, тесты CRUD проходят, `mark_expired` обновляет именно заданные ID.

### Этапы 3, 4, 5 — параллельно (после 2)

**Этап 3. Платформа (tt-platform)**

Трейт `WindowControl`; Linux/X11 через `x11rb`
(`_NET_ACTIVE_WINDOW`, `_NET_CLIENT_LIST`, `_NET_WM_PID`, MIT-SCREEN-SAVER — убирает
`xprintidle`); Linux/Wayland через `zbus`; Windows через `windows` + `sysinfo`. Порт
`utils.py`: трансформеры Telegram / Яндекс.Браузер / Steam → трейт `TitleTransformer`.

**Критерий готовности**: `WindowControl` возвращает корректные данные на X11 и Windows,
Wayland-реализация падает с понятным сообщением, трансформеры покрываются тестами.

**Этап 4. Звук (tt-audio)**

`rodio`: mp3/wav/ogg, `volume_offset` (дБ → линейный).
Без `ffmpeg` на чистой Windows.

**Критерий готовности**: все форматы воспроизводятся на Linux и Windows, громкость
изменяется корректно, ошибки обращения к отсутствующему файлу обрабатываются.

**Этап 5. Обновления (tt-updater)**

`reqwest` + `serde`, semver вместо самописного
`app_version_as_number`. Тесты на `wiremock`.

**Критерий готовности**: парсинг releases с GitHub работает, сравнение версий через
semver корректно, моки API покрывают случаи: нет релизов, ошибка сети, неверный формат.

### Этап 6. Сервисы (tt-tracker)

Требует этапы 2, 3, 4. `WindowTracker`, `IdleTracker`, `PomodoroTracker` (с собственным
таймером), `MainTracker`, `DeadlineChecker`. Исправления B1, B3, B5, B7. Замена
`while-running` цикла на `tokio::select!` с токеном отмены. Тесты на моках `WindowControl`
+ `tokio::time::pause()`.

**Критерий готовности**: все сервисы работают, баги B1, B3, B5, B7 покрыты тестами,
таймер Pomodoro тикает независимо от UI, корректная отмена через токен.

### Этап 7. UI (tt-app)

Требует этап 6. Порядок: Задачи → Настройки → Трекер → Статистика.

1. Оболочка (окно, навигация, тема, диалоги).
2. Дизайн-система (CSS-переменные из `ui/consts.py`).
3. Задачи (вложенность, дедлайны).
4. Настройки (трекеры, idle, Pomodoro, TZ, звук + секция «Запуск и трей»).
5. Трекер (кнопки, статус, обратный отсчёт).
6. Статистика (SQL-агрегация, фильтр по дате).

**Критерий готовности**: все экраны функциональны, навигация работает, тема переключается,
статистика обновляется корректно, фильтр по дате учитывает локальный часовой пояс.

### Этап 7.5. Трей и автозапуск (tt-system)

Требует этап 7. Меню трея (показать/скрыть, start/pause/resume/stop, статус, выход).
4 статусные иконки. Подписка на шину. `autostart` (Linux: `~/.config/autostart/*.desktop`,
Windows: реестр `Run`). `single-instance` (мьютекс / lock-файл). Переработанный жизненный
цикл окна: `close_to_tray` прячет окно (сессии продолжаются), реальный выход — только через
трей. Обработка `SIGTERM` / завершения сеанса ОС.

**Критерий готовности**: трей-меню открывается, команды работают, статус обновляется,
автозапуск включает/выключает, вторая копия активирует первую, close-to-tray прячет окно,
реальный выход завершает процесс, `SIGTERM` корректно останавливает трекинг.

### Этап 8. Сборка и релиз

`cargo-dist` (Linux x86_64 + Windows x86_64), `rust-embed` для ассетов. Проверка: запуск на
чистых Ubuntu 22.04 / 24.04 и Windows 10 / 11. **Проверить зависимость webview (R1).**

**Критерий готовности**: бинарники собираются на обе платформы, запускаются на чистых ОС,
webview работает, ассеты встроены, размер приемлемый (< 20 МБ).

### Этап 9. Паритет и переключение

Чек-лист функций Python vs Rust, обновление README (убрать требования `xprintidle` и
`ffmpeg`), переписывание `AGENTS.md` под Rust. Слияние ветки, архивация Python в теге.

**Критерий готовности**: все функции Python-версии реализованы, README обновлён,
`AGENTS.md` описывает Rust-архитектуру, ветка влита в main, Python-код архивирован.

| # | Риск | Митигация |
|---|---|---|
| R1 | Dioxus desktop тянет системный webview. Windows 10 без WebView2 не стартует; Linux нужен webkit2gtk-4.1. Регрессия относительно самодостаточного Flet | Проверить на этапе 0 **до** UI. Если неприемлемо — `dioxus-native` (WGPU) или `egui` |
| R2 | Активное окно в Wayland ограничено протоколом; только GNOME + `unsafe_mode` | Явная ошибка + подсказка вместо тихого пустого списка. Рассмотреть `xdg-desktop-portal` |
| R3 | Объём UI: 41 файл Flet, крупнейший `settings_form.py` — 324 строки | Порядок от простого к сложному. Форма настроек — последней |

| R5 | Чистый старт = потеря истории у существующих пользователей | Решено осознанно. Опционально — экспорт старой БД в CSV |
| R6 | В Python 5 тестов (все на парсер GitHub) — нет эталона поведения | Спорные места фиксировать как новые решения в тестах Rust |
| R7 | Bus factor: единственный контрибьютор | Этапы 1–6 без GUI, осваиваются постепенно; `clippy -D warnings` с начала |
| R8 | Трей в GNOME не работает из коробки: Shell убрал area уведомлений; `tray-icon` использует StatusNotifierItem, нужно расширение AppIndicator | Проверить на этапе 0 вместе с R1. Если иконки нет — не прятать окно, показать предупреждение. Приложение обязано работать без трея |
| R9 | `tray-icon` на Linux требует GTK и создания иконки в главном потоке; порядок инициализации критичен | Иконка строго в главном потоке до запуска loop; взаимодействие через каналы |

| R11 | Автозапуск прописывает абсолютный путь; после переноса файла запись битая | Перепроверять и обновлять путь при каждом старте, если автозапуск включён |

## 8. Критерии готовности

**Функциональные:** трекинг окон и бездействия на X11 / Wayland / Windows; Pomodoro с
